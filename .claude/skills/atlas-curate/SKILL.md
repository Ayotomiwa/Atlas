# atlas-curate

Read `../_shared/human-intents.md`, `../_shared/persistence-approval.md`, `../_shared/runtime.md`, `../_shared/answer-provenance.md`, `../_shared/agent-handoffs.md`, and `../_shared/curation-safety.md`. This is **Curate Atlas**. Successful evidence reconciliation and independent review produce authoritative `status: curated` knowledge; merge only distributes and audits it.

1. Read staging policy, the authoring prerequisites in the shared safety contract, and `references/semantic-preflight.md`. Default the queue scope to the user's current repository, domain, stable ID or named topic; show the package-wide queue only when requested. Use `python scripts/atlas_query.py staging --format json` and process coherent related `status: new` records. Do not mark them `curating` before the persistence preview is approved.
2. Read every source bucket contract and target curated README/template/index. Use exact IDs and typed `find` across aliases, descriptions, keywords and locators to identify semantic duplicate/target candidates; never silently select ambiguity.
3. Build a decision matrix per staging record and target: `CREATE`, `UPDATE`, `DEFER`, `REJECT` or `CONFLICT`. Staging must normally supply enough explanation and exact evidence for curation without broad product-source rediscovery. Curation may inspect precisely cited product evidence and browse Atlas broadly for duplicates, links and target context. If materially new product facts are needed, stage them first and issue a revised curation preview.
4. Ask one clarification round: required identity, scope, ownership, domain, promotion, conflict and safety decisions first, followed by one optional confirm-or-correct gap list. Skipped non-blocking gaps remain unknown. Present proposed outcomes in plain language before internal decision codes.
5. Complete the shared Git preflight. Reuse and state an existing feature branch; ask for a suggested/custom branch only on the default branch, detached HEAD or unrelated history. Record baseline `HEAD`, lint and freshness results. Show one preview covering the branch and local commit boundaries, selected staging status changes, curated files/claims, generated effects, unknowns, exclusions and independent review. Obtain one approval, then re-check queue state, branch, `HEAD`, actual content-clean state and exact scope. A newly claimed/changed record invalidates the preview.
6. Resolve the curating identity for `reviewed_by` from `git config user.name`, asking the user if Git has no usable identity. It records who curated the page, never the agent and never a later merger or publisher.
7. Pass the approved decision matrix, exact Git path scope, curating identity, original evidence routes and source ledger to `atlas-curator`. The curator materialises only supported changes and never requests the same approval. Inspect its diff and create the exact-path local checkpoint commit before validation repair.
8. Own aggregate lint classification, at-most-two mechanical repair passes, path-scope verification, generation and freshness. Never hand-edit generated artifacts. Commit validated repair/generated changes as specified by the shared contract. An unrelated baseline issue may defer freshness but cannot block semantic curation; a current-cause failure or unexplained lint/compiler inconsistency leaves active/new records from this batch `curating`.
9. Invoke `atlas-reviewer` independently over the immutable starting-to-proposal commit range plus exact source evidence. Verify the proposal `HEAD` and content-clean state before and after review. Apply only meaning-preserving fixes in exact-path local commits and re-review the full updated range. Semantic scope changes require a revised preview; recurring material findings stop for human judgment.
10. Mark successful evidence `consumed`, apply other approved outcomes, update the compact checkpoint and deterministic generated effects, then create the exact finalization commit. Report **Current work**, **Scope validation**, **Generated freshness**, and **Package health**, then trace claims, non-promoted material and questions. Local commits never authorise publication; later merge changes only the checkout advisory.

Create only the previewed local commits on the selected feature branch. Never push, merge, force-update, publish, bypass independent review, or hand-edit generated artifacts.
