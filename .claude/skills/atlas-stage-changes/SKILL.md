# atlas-stage-changes

Read `../_shared/human-intents.md`, `../_shared/persistence-approval.md`, `../_shared/runtime.md`, `../_shared/answer-provenance.md`, `../_shared/agent-handoffs.md`, `../_shared/source-analysis.md`, `../_shared/change-risk-analysis.md`, `../_shared/curation-safety.md`, `../_shared/clear-writing.md`, `_intake/README.md`, `_staging/README.md`, `_staging/index.md`, `_staging/changes/README.md`, `_staging/changes/_template.md`, and `references/workflow.md`. This is incremental **Sync Atlas**.

1. Resolve `ATLAS_ROOT`, the physical product Git root, the most-specific available Atlas repository context, source key, remote and default branch. Preserve missing, ambiguous and `not-verified` routing. If adequate full-baseline repository coverage does not exist, route to `atlas-onboard-repository` instead of asking the user to choose a workflow.
2. Load the shared checkpoint and its digest through `scripts/atlas_intake.py`. Fetch the remote default branch. If refresh fails, disclose that remote completeness is unknown and do not advance the shared checkpoint.
3. On first use, accept an explicit `--base <commit>`, a locally provable merged-MR commit, or the exact future-intake anchor recorded by an approved full onboarding snapshot. Never guess the initial cursor. Verify ancestry before assessing a range.
4. Inspect first-parent merges and direct commits from the exclusive cursor through the fetched tip. Use MR identity from local Git metadata or explicit user confirmation tied to the relevant default-branch commit; label the latter `user-confirmed`. Never require an external MR API.
5. Compare the range with all staging change provenance, route changed paths through resolved or explicitly ambiguous repository context and relevant Atlas records, then delegate substantial interpretation to `atlas-change-analyst`. Require the source-analysis causal explanation and the change-risk safety facts, non-symbol effects, cleared concerns, unresolved boundaries and smallest settling checks where the change can escape its local boundary.
6. Reconcile every logical change internally as `staged`, `no-stage`, `already-represented`, `deferred`, or `unassessed`. Use `no-stage` only when the traced behavior has no durable Atlas meaning inside the authorised boundary; diff size, absent symbol references and absent Atlas edges are insufficient. Use `deferred` when the change was assessed but a credible material boundary remains unresolved, and `unassessed` when required evidence could not be evaluated. Present plain-language groups first: new evidence to save, already covered, no durable Atlas impact, needs human information, and could not safely assess. Ask one consolidated material clarification round.
7. Show one shared persistence preview covering both staging files and the exact checkpoint compare-and-swap. Only after explicit approval complete the shared taxonomy/contract and destination-contract reads, then create one immutable-by-policy `staging.change` record per coherent reusable change, splitting only independent boundaries and drafting it with the shared clear-writing contract. Include required `change_source` provenance; flag sensitive paths without opening their contents or copying values.
8. Run Atlas lint. Record the fetched tip as observed and advance the considered cursor only when every change has an advancing outcome (`staged`, `no-stage`, `already-represented`, or `deferred`). Perform one compare-and-swap through `scripts/atlas_intake.py`, then lint again. Commit the exact staging records and checkpoint update atomically. A concurrent checkpoint change, rewritten history, source ambiguity, or failed commit stops completion; unreadable evidence or `unassessed` preserves the observed/considered distinction without deleting staged evidence.
9. Report branch/commit, dispositions, created records, unresolved items, checkpoint movement, validation, evidence references and material file hops. If staging succeeded but checkpoint update/commit failed, leave the scoped diff inspectable and say the next run must detect the records as `already-represented`.

Never curate, edit existing committed staging evidence beyond lifecycle status, hand-edit generated files or checkpoint JSON, push, merge, force-update, approve, or claim that an unrefreshed local ref is the remote default-branch tip.
