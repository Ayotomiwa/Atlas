# Persistence preview and approval contract

Use one preview and one explicit approval for one unchanged persistence scope.

Before writing, apply the Git preflight to the repository receiving the change. Require actual content-clean staged/unstaged state and no non-ignored untracked files; do not treat Windows stat-only status entries as content changes. Reuse an existing non-default branch with shared default-branch history, state `Using feature branch <name>` once, and warn without blocking when it is behind. Do not create a branch per Atlas write. On the default branch, detached HEAD, or unrelated history, stop and ask the user to confirm the suggested `feature/atlas-<intent>-<scope>-YYYYMMDD`, select an existing branch, or supply a custom valid Git branch.

The preview states what was found; the exact records/files and claims to save or change; evidence/provenance; scope/confidence/unknowns; existing or conflicting knowledge; required user decisions; exclusions; validation and intake effects; the feature branch; and planned local commit boundaries. Carry that approval through internal handoffs without asking again. Re-preview only when claims, targets, files, evidence boundary, destructive effects or checkpoint range materially change.

After approval, the parent may create only the previewed local commits on that branch. Use exact-path `git add -- <paths>`; never use `git add .`, broad resets, hook bypass, push, merge, force-update, approval or publication. Ordinary writes use one validated commit, merged-change intake commits evidence plus its checkpoint atomically, and curation follows the shared checkpoint/validated/finalization sequence. A failed commit leaves the scoped diff inspectable. Related later writes may reuse the branch but need a new preview for a new content scope.

For curation, separate **Current work**, **Scope validation**, **Generated freshness**, and **Package health**; distinguish current blockers from unrelated baseline advisories and any deferred freshness. Then lead with saved/changed, already covered, left unknown, deferred, excluded and next publication step. Global lint/CI remain strict; stable IDs and lifecycle/disposition codes are audit detail.
