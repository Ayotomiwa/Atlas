# Generated maps

## Purpose

`_curated/maps/` contains deterministic machine-readable projections of relationships authored on curated Markdown pages.

**Pages explain concepts. Maps connect concepts.** Maps exist primarily for routing, graph traversal and impact analysis; they are not a parallel knowledge-authoring surface.

## Source of truth

Curated page frontmatter `relationships:` is authoritative for relationship authorship. The JSON files in this directory are generated by `scripts/rebuild_maps.py`.

Never hand-edit relationship data in a map. A manual map change without the corresponding page relationship is drift and must fail validation.

Every generated map declares metadata including:

- `schema_version: atlas-map/1.0`;
- `generated: true`;
- generator `scripts/rebuild_maps.py`;
- package `teama`;
- source of truth `_curated/**/*.md`.

## Map responsibilities

| Map | Use it for | Do not use it for |
|---|---|---|
| `flow-component-map.json` | flow participation, flow-to-flow dependencies and reverse routing from components/infra to flows | detailed component contracts or full infra resource modelling |
| `repo-dependency-map.json` | component consumes/produces/depends-on relationships and reverse dependency lookup | flow narrative or infrastructure package internals |
| `infra-dependency-map.json` | infra dependencies, deployment/resource-use relationships and reverse routing to users | component implementation detail or business/data semantics |

Runbook, incident and standard relationships may be surfaced as routing metadata but do not create a fourth V1 map.

## Which map to start with

| Question | Start with |
|---|---|
| Which components participate in flow X? | `flow-component-map.json` |
| Which flows include component Y? | reverse view in `flow-component-map.json` |
| What does component Y consume, produce or depend on? | `repo-dependency-map.json` |
| What depends on component Y? | reverse view in `repo-dependency-map.json` |
| What infra deploys/supports a component or flow? | `infra-dependency-map.json` |
| What could be affected by changing infra X? | `infra-dependency-map.json`, then linked pages/flows/components |

Use the map to find the route, then open the relevant curated pages for explanation, evidence and coverage limits.

## Confidence and safe impact language

Generated edges preserve relationship-level confidence from curated pages. Impact analysis should separate:

- **known affected** — supported by reviewed relationships/evidence;
- **possibly affected** — possible/unconfirmed/conflicting relationship evidence;
- **unknown / not covered** — Atlas does not contain enough reviewed context.

Never claim "not affected" simply because a reverse edge is absent.

## Generation workflow

After any curated relationship change:

```bash
python scripts/rebuild_maps.py
```

Before proposing/merging:

```bash
python scripts/rebuild_maps.py --check
```

`--check` compares committed generated output with what current curated pages would generate. CI runs the freshness check so page/map drift cannot silently accumulate.

## Consistency examples

- component `atlas.participates-in` flow → projected into `flow-component-map.json`;
- component `atlas.consumes` / `atlas.produces` / `atlas.depends-on` → projected into `repo-dependency-map.json`;
- infra `atlas.depends-on` / `atlas.deployed-by` and relevant infra/resource usage → projected into `infra-dependency-map.json`;
- reciprocal views are derived from authored forward edges rather than duplicated as separate source-of-truth relationships.

## Do not

- do not recreate one catch-all `dependency-map.json`;
- do not author facts directly in JSON maps;
- do not put long narrative explanations in maps;
- do not infer certainty from missing edges;
- do not use generated maps as a substitute for the evidence and coverage notes on curated pages.
